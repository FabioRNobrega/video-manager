## Problem Statement

`WebApp/WebApp.Client/Components/VideoLibrary.razor` currently renders a static JPEG thumbnail per video, generated by the FFmpeg pipeline in `Specs/20260831104814-static-video-thumbnails-ffmpeg/`. A single frame does not convey what a video actually contains. This specification adds a second, independent derived-media asset — a short, muted, looping MP4 preview built from three sampled sections of the source (~20%, 50%, and 80% of its duration) — that replaces the static thumbnail only while the user hovers a card, and reverts to it immediately when the pointer leaves or the preview is not yet available. It extends, and does not replace, the existing static-thumbnail feature: every existing FR from the prior spec continues to hold unchanged.

## User Stories

- Given a video whose static thumbnail is already `Ready`, when a user keeps the pointer over its card for about 300ms, then the card's image is replaced by a short looping muted preview sampled from three points in the video.
- Given a user moving the pointer away from a card, when `mouseleave` fires, then the preview stops immediately and the static thumbnail reappears without delay.
- Given a video whose hover preview has not finished generating (or failed, or is disabled), when the user hovers its card past the delay, then the static thumbnail simply remains visible with no error state.
- Given a freshly discovered video, when the library is scanned, then its static thumbnail becomes available exactly as it does today, and its hover preview is generated afterward in the background without delaying the scan or the thumbnail.
- Given a video whose source file changes, when the library is rescanned, then both its old static thumbnail and its old hover preview become unreachable under the new identity, exactly mirroring the existing thumbnail invalidation rule.
- Given the operator finds hover-preview generation too heavy for the host, when they set `HoverPreview:Enabled` to `false`, then no preview work is ever queued or served and the static-thumbnail pipeline keeps working exactly as before.

## Functional Requirements

1. **FR1 — Independent derived asset:** The hover-preview pipeline must be introduced as parallel, separate types beside the existing thumbnail pipeline. `ThumbnailCache`, `ThumbnailCoordinator`, `ThumbnailBackgroundWorker`, `ThumbnailJobQueue`, `FfmpegThumbnailGenerator`, and `IThumbnailGenerator` must not be renamed, merged, or generalized into shared `Media*` types by this spec.
2. **FR2 — Preview output contract:** A successful preview generation must produce one MP4 file, H.264 video, no audio track, scaled to a configured width (default 480px) preserving the source aspect ratio, at a configured frame rate (default 15fps), encoded with `-movflags +faststart` so it is playable while streaming, regardless of whether the source is `.mp4`, `.webm`, `.mov`, or `.m4v`.
3. **FR3 — Reused duration probing:** Preview generation must obtain the source's duration through the existing `IVideoDurationProbe` abstraction (no second FFprobe service). Duration probing happens inside the new generator, mirroring how `FfmpegThumbnailGenerator` already probes duration before computing its seek.
4. **FR4 — Deterministic sample plan:** For a source with a probed duration of at least 15 seconds, the generator must compute exactly three sample start times at approximately 20%, 50%, and 80% of the duration, each spanning a configured segment length (default 1.5s), clamped so no segment start plus its length exceeds the duration minus a small safety margin.
5. **FR5 — Short-video fallback:** For a probed duration below 15 seconds but at or above 3 seconds, the generator must produce a single segment of up to 3 seconds starting at time zero instead of three segments. For a probed duration below 3 seconds (and above zero), it must produce a single segment spanning the duration minus a small safety margin, starting at time zero. No segment may ever be computed to start at or extend past the end of the source.
6. **FR6 — Unprobeable duration fails cleanly:** When duration cannot be determined (probe failure, zero, or negative), preview generation must return a structured `Failed` result without invoking the main FFmpeg encode step, without crashing the worker, and without blocking other queued jobs.
7. **FR7 — Focused generator abstraction:** A new `IHoverPreviewGenerator`/`FfmpegHoverPreviewGenerator` pair must accept an already-validated `VideoFileEntry` and a server-resolved destination path, invoke FFmpeg, and return a structured `Success`, `Failed`, or `Cancelled` result, without discovering files, managing queues, serving HTTP, or referencing Blazor — mirroring `IThumbnailGenerator`'s contract shape with its own result type.
8. **FR8 — Safe process invocation:** The FFmpeg invocation for previews must use `ProcessStartInfo` with `UseShellExecute = false` and `ArgumentList` (never a shell string), reusing the same safety pattern as `FfmpegThumbnailGenerator`: re-validated source metadata before start, asynchronous bounded/redacted stderr capture, `WaitForExitAsync` with cancellation, process-tree termination and temp-file cleanup on cancellation, and exit-code verification.
9. **FR9 — Multi-segment concatenation:** For a three-segment sample plan, the FFmpeg invocation must seek to each sample position with its own input, strip audio, scale/frame-rate each segment identically, and join them with FFmpeg's `concat` filter into one continuous output; for a single-segment plan, it must trim/scale/frame-rate that one segment directly without a concat filter.
10. **FR10 — Atomic publication:** FFmpeg must write to a unique temporary MP4 file. The generator must verify a non-empty readable output before atomically moving it to the final cache filename; failed, cancelled, or abandoned temporary outputs must be deleted when possible. A concurrently published valid final file counts as success without overwrite.
11. **FR11 — Private preview cache:** Preview files live under a `hover` subdirectory of the already-validated `ThumbnailCache:Path` root (no new top-level configured path, no new Docker volume). The cache key is computed the same way as the thumbnail cache key (normalized root-relative path, size, UTC last-write time, SHA-256), using a distinct version marker so preview and thumbnail hashes never collide, intentionally implemented as its own small function rather than a shared extraction from `ThumbnailCache` at this stage.
12. **FR12 — Cache reuse:** Before queueing or generating work, a valid non-empty final MP4 for the current preview cache key must be treated as `Ready`, and FFmpeg must not be invoked again for it.
13. **FR13 — Separate bounded job queue:** A new `IHoverPreviewJobQueue`/`HoverPreviewJobQueue`, independent from `IThumbnailJobQueue`, must provide a finite, configurable, non-blocking, deduplicated (per cache key) queue, mirroring the existing queue's `Channel`-based design without sharing its instance or registration.
14. **FR14 — Separate sequential worker:** A new `HoverPreviewBackgroundWorker` (a `BackgroundService`, registered independently of `ThumbnailBackgroundWorker`) must consume one preview job at a time, continue after an individual failure, log start/success/failure/cancellation using the opaque media ID and/or cache-key prefix (never a physical or root-relative path), and honor host-shutdown cancellation.
15. **FR15 — Thumbnail-first scheduling:** The preview coordinator must not enqueue a preview job for a video whose static thumbnail is not yet `Ready` (checked by calling the existing `ThumbnailCoordinator.Resolve`, without modifying it). This gives the higher-value static thumbnail effective priority without a general priority queue.
16. **FR16 — Non-blocking scan integration:** `VideoLibraryService.ScanAsync` must, after publishing its snapshot and reconciling thumbnail work exactly as today, also reconcile hover-preview work through the new coordinator, and return without awaiting any FFmpeg-family process.
17. **FR17 — Single failure attempt:** A failed preview cache key must enter `Failed` for the remainder of the current server process and must not be retried by reconciliation or rescanning during that process, mirroring the thumbnail pipeline's failure policy with its own independent failed-key set.
18. **FR18 — Source-change safety:** Before launching FFmpeg, the worker must confirm the queued source still matches the validated size and last-modification metadata captured at scan time; a changed, missing, or unreadable source must not publish a preview under the stale cache key.
19. **FR19 — Independent preview state:** A new client-side `HoverPreviewState` enum (`Unavailable`, `Pending`, `Ready`, `Failed`) must represent preview availability independently of the existing `ThumbnailState`; a video may simultaneously report a `Ready` thumbnail and a `Pending`/`Failed`/`Unavailable` preview.
20. **FR20 — DTO extension:** `VideoItemDto` must gain a `HoverPreviewState` and a nullable `HoverPreviewUrl`, populated only when the state is `Ready`, kept separate from `ThumbnailState`/`ThumbnailUrl`, and must never expose cache keys or filesystem paths.
21. **FR21 — Protected preview endpoint:** A new `GET /api/videos/{id}/preview` endpoint must resolve the opaque ID through the current snapshot exactly like the existing stream/thumbnail endpoints, derive the expected cache file internally, and return `video/mp4` with range processing enabled only when the file is valid and `Ready`; otherwise it must return `404`. It must not accept arbitrary paths or expose the preview cache directory through static-file middleware.
22. **FR22 — Global enable/disable switch:** A new `HoverPreviewOptions.Enabled` flag (default `true`) must, when `false`, prevent the coordinator from ever enqueueing preview work, make the preview endpoint always return `404`, and make every DTO report `Unavailable`/`null`, while leaving the thumbnail pipeline completely unaffected.
23. **FR23 — Default-image card behavior:** `VideoLibrary.razor` must keep rendering the existing `<img>` thumbnail as every card's default state. It must not request or preload every video's hover preview when the library is opened or rescanned.
24. **FR24 — Per-card hover tracking:** The component must track which single opaque video ID is currently being considered or shown for preview (not an anonymous shared boolean), so hovering one card can never activate or cancel the preview of another card.
25. **FR25 — Entry delay, immediate exit:** On `mouseenter`, the component must start an approximately 300ms delay before activating a card's preview, cancelling that delay if the pointer leaves first. On `mouseleave`, it must cancel any pending delay and, if a preview was already showing, immediately remove it and restore the static thumbnail with no delay.
26. **FR26 — Graceful non-ready hover:** If, when the entry delay elapses, that video's `HoverPreviewState` is not `Ready`, the card must simply continue showing its current static-thumbnail state; it must not show an error, spinner, or blank area.
27. **FR27 — Lightweight, non-interactive playback:** When a preview is shown, it must render as a `<video>` element configured for autoplay, muted, loop, and inline playback, with no visible controls, using the card's existing thumbnail URL as the poster, filling the same `.ratio-16x9` cover-sized container as the image with no layout shift.
28. **FR28 — Unchanged selection semantics:** Showing or hiding the hover preview must not change the card's existing button/`OnSelect` click behavior, keyboard focus, or the selected-state badge.

## Non-Functional Requirements

- **Responsiveness:** Library discovery and thumbnail availability must remain completely independent of hover-preview generation; a scan or a thumbnail's readiness must never wait on preview FFmpeg work.
- **Resource control:** At most one hover-preview FFmpeg process runs at a time in this MVP. The preview job queue is finite and configurable, defaulting to a small capacity appropriate for heavier video-encoding work. The whole pipeline can be disabled at runtime via `HoverPreview:Enabled` without a redeploy.
- **Security and privacy:** Only `VideoFileEntry` instances from the existing validated scan may become preview jobs. No request parameter may become an FFmpeg path. Preview cache keys, root-relative paths, and physical paths must never reach browser responses or normal logs — only opaque IDs, cache-key prefixes, and safe application URLs.
- **Source integrity:** The `/videos` mount remains read-only and untouched; preview generation writes only inside the `hover` subdirectory of the existing preview cache root.
- **Failure isolation:** FFmpeg process-start failures, corrupt/unsupported input, unprobeable duration, permission errors, and cancellation must never crash the host, the preview worker, or the thumbnail pipeline.
- **Cache consistency:** Only a verified, complete MP4 may be served. Preview cache keys follow the same source-identity invalidation rule as thumbnails (changed size/mtime ⇒ new key ⇒ old asset unreachable).
- **Testability:** Preview identity, sample-plan computation, queueing, coordination, and endpoint behavior must be exercisable with the same fake/seam-based approach already used for the thumbnail pipeline's tests, without requiring a real video library.
- **Accessibility:** The preview `<video>` is decorative (the card title remains the accessible name) and must not introduce keyboard traps or new focusable controls.
- **Touch/non-hover devices:** The card must remain fully usable (selectable, playable) on devices without hover; no touch-specific preview behavior is introduced in this slice.
- **Workflow:** Build, run, and test validation continue exclusively through the repository's Docker Compose-backed `Makefile` commands, matching every prior spec in this repository.

## Out of Scope

- Scene-change detection or any non-percentage-based sample selection.
- Configurable sample count/positions beyond the fixed 20/50/80% (three-segment) and short-video fallback rules defined here.
- SignalR, WebSockets, or any push-based update mechanism for preview readiness (the client already polls `GET /api/videos`, which now also carries preview state).
- A database, persistent job/status records, or a cache-index database.
- A second Docker container/worker process; the preview worker runs in the existing single ASP.NET Core container.
- A shared FFmpeg-process concurrency limiter between the thumbnail and preview workers — only introduce one later if real measurement shows contention; not built speculatively here.
- Refactoring `ThumbnailCache`/`ThumbnailCoordinator`/`ThumbnailBackgroundWorker`/`ThumbnailJobQueue`/`FfmpegThumbnailGenerator` into shared `Media*` abstractions, or extracting a shared identity-hashing/process-runner utility between the thumbnail and preview generators — deferred until a third derived asset makes the duplication concrete.
- ASP.NET Core Identity, ACLs, or authorization policy implementation (the new endpoint is shaped so a future authorization layer can apply uniformly, but none is added here).
- Touch-device tap-to-preview, orphaned-preview garbage collection, and retrying a failed preview key within the same server process.
- Suppressing the hover preview for `prefers-reduced-motion: reduce`. This project currently respects that preference only through pure CSS `@media` rules (see `WebApp/WebApp/wwwroot/app.css`); detecting it in Blazor to conditionally skip rendering the `<video>` element would require new JavaScript interop, which this task's scope explicitly excludes. Deferred to a future slice if desired.
- Any change to the original video stream endpoint, the reframing editor, playback controls, theme, or Fill-tab behavior.

## Open Questions

None. MVP decisions confirmed on 2026-08-31: short-video fallback threshold is 15 seconds probed duration, with a single ~3-second segment from the start below that (and a whole-clip-minus-safety-margin segment below 3 seconds); a dedicated `HoverPreview:Enabled` configuration switch (default `true`) is included as an operational safety valve independent of the thumbnail pipeline's configuration.
