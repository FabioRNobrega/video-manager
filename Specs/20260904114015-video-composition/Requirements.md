## Problem Statement

`Specs/20260903190117-video-cut-export/` added a "Cuts" section (`Home.razor`) that lists A/B exports produced from library videos, browsed through the shared `VideoGrid.razor` component. There is currently no way to combine several of those cuts into a single, longer video: a user who has cut several clips from the same source (e.g. numbered `Jennifer White 0001.mp4`, `0002`, `0003`) has no way to join them into one browser-playable file with smooth transitions between clips. This feature adds a "Create Composition" action to the Cuts section that lets a user select multiple existing cuts, sends only their opaque IDs to the server, and runs a background FFmpeg pipeline that normalizes each selected clip to a common resolution/frame-rate/audio format, applies fade-in/fade-out transitions at each clip boundary, concatenates them in filename order, and publishes the result as a new browser-friendly MP4 that appears in a new "Video Compositions" section exactly like any other NAS video.

## User Stories

- Given the Cuts section is showing cut videos, when the user views each card, then a checkbox appears in its top corner that toggles selection without triggering the existing "select for playback" click behavior, and a running count of selected clips is shown (e.g. "3 clips selected").
- Given at least 2 cuts are selected, when the user clicks "Create Composition", then the browser sends only the selected cuts' opaque IDs to the server and immediately shows the new job as "Pending" without waiting for FFmpeg to finish.
- Given fewer than 2 cuts are selected, when the user looks at the "Create Composition" action, then it is disabled so a composition of 0 or 1 clip cannot be requested.
- Given a composition job is Processing, when the user looks at the "Video Compositions" section, then the job is listed with a visible status (Pending/Processing/Completed/Failed) without the user needing to perform any video processing client-side.
- Given a composition job completes successfully, when the user looks at the "Video Compositions" section, then the produced video appears there as a normal card in the same `VideoGrid` layout used by Library and Cuts — with a working thumbnail and hover preview, generated the same way an ordinary library video's or cut's is — without the user needing to rescan or refresh the page.
- Given the Video Compositions section lists a completed composition, when the user clicks its card, then it opens in the same `VerticalVideoEditor` used for library videos and cuts, in the center of the page, and the user can watch the full rendered result (all clips, in order, with the fade transitions applied) using the same playback controls (play/pause, seek, volume, speed, fill-tab) as any other video — the composed video is a first-class, fully playable NAS video from this point on, not a special-cased preview.
- Given a composition job fails (e.g. `ffprobe`/`ffmpeg` error on one of the inputs), when the user looks at the "Video Compositions" section, then the job shows "Failed" and no partial/corrupt file appears in the video library; diagnostic detail is available in the server logs, not necessarily the UI.

## Functional Requirements

1. FR1 — `VideoGrid.razor` gains an optional selection mode: when enabled for a grid instance, each card renders a checkbox (`<input type="checkbox">` or equivalent Bootstrap-styled control) pinned to its top corner (e.g. `position-absolute top-0 start-0`), independent of the existing `SelectedId`/`OnSelect` "open in editor" click behavior, so a user can check clips without navigating away from what they're currently viewing.
2. FR2 — Selection state (the set of checked cut IDs) is owned by `Home.razor` (client-only; never persisted server-side) and is scoped to the Cuts grid only, per the confirmed decision — the main Library grid does not gain a composition checkbox.
3. FR3 — `Home.razor`'s Cuts section shows a running "N clips selected" count and a "Create Composition" button, enabled only when `N >= 2` (confirmed minimum), following the existing `btn-primary`/`btn-secondary` hierarchy convention.
4. FR4 — Clicking "Create Composition" posts `{ videoIds: string[] }` (the selected cuts' opaque IDs only — never file paths) to a new `POST /api/compositions` endpoint, then clears the selection and shows the returned job in a pending state.
5. FR5 — The endpoint resolves every submitted ID through the existing `IVideoCutService.TryResolve` (only current-snapshot opaque cut IDs are accepted; unresolvable IDs return `400`), rejects requests with fewer than 2 valid IDs (`400`), and enqueues a composition job without performing any FFmpeg work inline, returning `202 Accepted` with a job id.
6. FR6 — A new background worker drains composition jobs one at a time (mirroring `CutBackgroundWorker`/`ICutJobQueue`). Before rendering, it orders the job's resolved `VideoFileEntry` list by `Name` (ordinal string comparison), so the existing `NNNN` zero-padded numeric naming convention already used for cuts (and library sources) produces the correct playback sequence.
7. FR7 — For every ordered input, the worker runs `ffprobe` (a new `IVideoCompositionProbe`/`FfprobeCompositionProbe`, separate from the existing lightweight `IVideoDurationProbe`/`IVideoResolutionProbe` used for grid display) to read width, height, duration, frame rate, video codec, audio codec, audio sample rate, and audio channel count for that specific file. A probe failure on any input fails the whole job (FR15) before any FFmpeg render step runs.
8. FR8 — The worker selects the output canvas resolution as the width/height of the probed input with the smallest pixel count (`width * height`), preserving that input's aspect ratio. Every clip is scaled down to fit within that canvas without upscaling (a clip already at or below the target size is only padded/letterboxed, never enlarged) using a scale-down-and-pad filter chain, and the target frame rate is the lowest of the probed inputs' frame rates (never interpolated up) so no source is upsampled.
9. FR9 — The worker selects a single common audio format for all clips (fixed sample rate and channel layout, e.g. 48 kHz stereo AAC) applied uniformly during normalization, so every normalized clip has byte-compatible audio parameters before concatenation regardless of each source's original sample rate/channel count.
10. FR10 — For each ordered clip, the worker computes fade points from a configurable `TransitionDuration` (default `TimeSpan.FromSeconds(5)`, clamped per-clip to at most half that clip's own duration so a fade never overlaps itself on a short clip): the first clip gets only a fade-out at its end; every middle clip gets a fade-in at its start and a fade-out at its end; the last clip gets only a fade-in at its start. Fades never overlap between adjacent clips (each clip's own fade happens within its own duration), so total output duration remains approximately the sum of all input durations.
11. FR11 — The worker normalizes each clip to the chosen canvas/frame-rate/audio format while applying its computed fade filters (video `fade`, audio `afade`) via `ffmpeg`, writing each normalized clip to its own temporary file (not held in memory) to keep the MVP debuggable, then concatenates the normalized temporary files in filename order into the final H.264/AAC MP4 output using `ffmpeg`'s concat mechanism.
12. FR12 — All FFmpeg/ffprobe invocations in this pipeline use `ProcessStartInfo`/`ArgumentList` only (never a shell string), matching the existing thumbnail/cut generators' constraint.
13. FR13 — The final output is written to a temporary path first and only atomically published (`File.Move`, no overwrite) into `<VideoComposition__Path>` (a new writable root, sibling to `<VideoCut__Path>`) after FFmpeg exits successfully and the output file is verified non-empty/readable — matching `FfmpegCutGenerator`'s existing temp-then-move publish pattern.
14. FR14 — All per-clip temporary normalized files and the temporary final-output file are deleted after a successful publish. They are also deleted (best-effort) on failure or cancellation, leaving no partial/temporary file behind in `<VideoComposition__Path>`.
15. FR15 — On any probe or FFmpeg failure, the job is marked Failed with a redacted diagnostic (source/temp/destination physical paths replaced the same way `FfmpegCutGenerator.Redact` already does) logged at `Warning`/`Error`, identifying which input clip and which stage (`probe`, `normalize`, `concat`) failed; no file is published to `<VideoComposition__Path>` for a failed job.
16. FR16 — The output file name is `<two-word prefix of the first clip in filename order> Composition <NNNN>.mp4` (e.g. `Jennifer White 0001.mp4` + `Jennifer White 0002.mp4` → `Jennifer White Composition 0001.mp4`), using the same two-word-prefix extraction already implemented by `CutNamingService.GetPrefix` and the same "list existing files, take `max + 1`" 4-digit counter approach, scoped per distinct prefix — per the confirmed naming decision, this uses the first ordered clip's prefix regardless of whether other selected clips share it.
17. FR17 — A new `GET /api/compositions/jobs` endpoint (or equivalent) returns the current known composition jobs (in-memory for this process's lifetime) with id, status (`Pending`/`Processing`/`Completed`/`Failed`), and — once resolvable — the resulting composition's opaque video id, so the Blazor client can poll and render status without performing any video processing itself.
18. FR18 — A new `GET /api/compositions` endpoint lists the current contents of `<VideoComposition__Path>` the same way `GET /api/cuts` lists `<VideoCut__Path>` (extension allowlist, symlink/reparse-point skip, canonical containment check), addressed by their own opaque, snapshot-scoped IDs, and a `GET /api/compositions/{id}/stream` (plus thumbnail/preview endpoints reusing `ThumbnailCoordinator`/`HoverPreviewCoordinator`/`VideoMetadataCoordinator` against this new service) mirrors the equivalent `Cuts` endpoints so composed videos get thumbnails, hover previews, and range-enabled playback identically to library videos and cuts.
19. FR19 — `Home.razor` renders a new "Video Compositions" section below the existing "Cuts" section, using `VideoGrid.razor` for completed compositions (loaded via `GET /api/compositions`) plus a job-status list/badges sourced from `GET /api/compositions/jobs` for Pending/Processing/Failed jobs; it polls both endpoints (matching the existing 2-second cuts-polling pattern) while any job is not yet in a terminal state, and stops once none remain pending/processing.
20. FR20 — Once a composition job's worker publishes its output successfully, it triggers the composition service's rescan (mirroring `IVideoCutService.ScanAsync` being called from `CutBackgroundWorker`) so the newly composed video is immediately visible via `GET /api/compositions` without requiring a manual rescan or app restart.

## Non-Functional Requirements

- FFmpeg/ffprobe invocation for this pipeline follows the existing `ProcessStartInfo`/`ArgumentList`-only, no-shell-string constraint; per the confirmed FFmpeg-scope decision, `AGENTS.md`'s FFmpeg constraint is widened with a new, narrowly-scoped exception for this composition pipeline specifically (fixed source roots: the video library and `<VideoCut__Path>`; fixed destination root: the new `<VideoComposition__Path>`; no other new FFmpeg use is authorized by this spec).
- The composition job queue/worker must not block the request thread; `POST /api/compositions` returns immediately after enqueueing (`202 Accepted`), matching the non-blocking pattern already used for cuts.
- All composition-related endpoints resolve videos only through opaque, snapshot-scoped IDs; no physical or root-relative path may reach the browser or be written to normal application logs (same boundary as `Constraints` in `AGENTS.md`); diagnostic logs redact physical paths the same way `FfmpegCutGenerator.Redact` already does.
- The composition service/generator/queue/worker/probe are separated by responsibility the same way the cut pipeline is (dedicated interfaces per concern: probe, generator, queue, worker, naming, listing service) so each piece stays independently testable with fakes, per existing `WebApp.Tests/Services` conventions.
- Because rendering can take several minutes for multiple clips, the design must not hold an HTTP request open for the duration of FFmpeg processing; job status must be pollable at any time via FR17.
- The design should keep working when `<VideoComposition__Path>` is briefly unavailable (surface a scan/job failure) rather than crashing the host, matching the existing Cuts folder resilience expectation.

## Out of Scope

- Selecting videos for composition from the main Library grid (composition selection is Cuts-section-only, per the confirmed decision).
- Manual reordering of clips within a composition; order is always derived from filename (`Name`, ordinal compare) and cannot be overridden by the user.
- Overlapping/cross-fade transitions between adjacent clips (this MVP's fades are non-overlapping — each clip fades within its own duration, not into the next clip's content).
- Deleting/renaming/managing existing compositions through the UI (only creation and browsing, matching the existing Cuts pattern).
- Composing a composition's own output (composing already-composed videos) — out of scope for this MVP; the composition source list is drawn only from cuts.
- Editing an in-flight or completed composition job (no cancel/retry/re-run UI).
- Cross-machine or multi-user job coordination, or persisting job history across an app restart (in-memory job registry only, consistent with this app's existing single-process, local-only design).
- Configurable transition duration through the UI; `TransitionDuration` is a fixed server-side constant/config value for this MVP.
